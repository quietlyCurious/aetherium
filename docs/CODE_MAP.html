Aetherium Code Map

How the whole app is put together: the two workspaces and their areas, which file owns what, how a setting or a model's data travels to a box on screen, how the Screens editor is split, and the handful of patterns everything leans on.

Status: both refactors complete The Operator side is 45 modules and 7 stylesheets under src/operator/ (was one 9,074-line file). The designer side and the app shell are 29 files under src/designer/ and src/shell/, and App.js is down from 3,202 lines to 630. Every industry model now uses the one generic data format.

At a glance

The app has two workspaces, picked from the title-bar menu. The Operator Experience is the next-gen HMI for someone running the plant. The Configuration Experience is where things get set up: Visualization (how each asset type and asset displays), the page builder (Screens, Widgets, Theme) and the data definitions (Data Sources, Entities, Queries, Asset Sets, Scripts).

Every area gives App the same handle: save() for the title-bar Save, and confirmLeave() (true, or a promise of true, to go ahead). Only the area being left is asked. The Operator side: how it's wired

Both the Operator Experience and Visualization are one component, OperatorWorkspace, told apart by operatorPersona. It waits for the chosen model's data (model/useLoadedModel, which Screens uses too), then hands off to OperatorWorkspaceInner, where all of the interface's state lives. App.js talks to it through a ref: save(), confirmLeave(), resolveUnsavedChanges() and toggleListPanel().

Two things in this picture are unusual and worth knowing before reading code:

  • The loaded model lives in module-level variables, not in React state. They're in model/modelData.js, and only that file writes them: the loader calls activateLoadedModel(), then remounts OperatorWorkspaceInner (its React key is model + persona). Everything else imports and reads them, which is why switching models always starts the interface fresh.
  • Deep components get shared data from three small stores rather than props passed down every layer. They're covered under Patterns to know.

The Operator side: screen → component

The workspace is a set of slots. The left rail (shell/AreaRail) picks what goes in the left list and the center. The right rail picks what the right panel shows. In the Operator Experience the rail is the workspace's own: Attention, Work and Assets, which set railMode. In the Configuration Experience the rail is App's, drawn outside the workspace: Visualization (this workspace, railMode 'now'), then Screens, Widgets and Theme, then Data Sources, Entities, Queries and Scripts.

The settings chain

Everything a Configurator user sets is stored twice over: once per type and optionally per asset. That's six kinds of setting at two levels, twelve stores in all, plus the one global All Assets template. They all live as useState in OperatorWorkspaceInner, each backed by its own storage file.

The rule that matters most: AssetCard is the single place the asset-over-type fallback is applied for display. Operator's Assets view, Investigate, Cards, Diagram and All Assets all render boxes through it. A new per-asset setting should be resolved there, not special-cased per view.

The rendering stack

A handful of building blocks are reused everywhere, from a single number tile up to whole views. Knowing these four layers explains most of the file.

Model data, from file to screen

An industry model is data only: a folder under public/data/<id>/ and an entry in models.json. Every model uses the generic format (INDUSTRY_PACK_SPEC.md §6): any hierarchy depth, everything keyed by real asset id, its own timeline. There are no model names or id conversions anywhere in src/operator/.

Screens: the editor and the renderer

The Screens area builds pages from containers and DevExtreme widgets, and binds widget properties to expressions or to queries. It's split three ways: state (a hook App holds), edits (plain functions), and drawing (the workspace and its panels). A saved page renders read-only through the same ContainerCard the canvas uses, so a screen looks the same wherever it shows.

  • A page is { id, name, folderId, containers, breakpointOverrides, … } in localStorage aetherium_pages. Containers nest; a grid container's cells each hold one cell container. Each container carries a slot (flex placement and box model), a coord (for coordinate layouts), per-tier breakpointOverrides, and a widget's widgetProps and bindings.
  • A binding is { type: 'expression', expression } or { type: 'query', queryInstanceId, outputField | outputFields, transform }. Adding a kind of binding (say, a property of the asset a screen is showing) is one entry in BINDING_RESOLVERS.
  • Query instances put a query on a page (aetherium_query_instances). Their ids restart at 1 per page, so every lookup is scoped to the page (plus app-scoped instances).
  • Locks: a locked container, or anything under one, can't be edited, moved, deleted, painted or pasted into. The checks (LOCK GUARD) live in useScreenEditor, not in the edit functions.

The data areas

Data Sources, Entities, Queries and Asset Sets are each a list of definitions plus an editor, and share one shell, designer/DefinitionWorkspace. It owns selection, the confirm-before-losing-edits prompt, and publishing the open editor's unsaved state. Each area supplies its nouns, its list columns and its editor; an editor exposes isDirty() and save() on its ref, and useDefinitionDraft does both for a simple form. The definitions themselves live in App (data sources, entities, queries, asset sets), because Screens reads the queries too, and will read asset sets.

Asset sets (model/assetSets.js) are named ways of producing a list of asset ids from the loaded model: picked (a hand-chosen list), rule (where to look, types, attention, property conditions, and optionally the lowest or highest N by a property) or query (not built yet). A rule can look under a start asset it's given when it's used, the way a query takes inputs: "Turbines of a feeder" is one definition, and a feeder screen would pass its own feeder. Unlike the other definitions, a set belongs to one model (modelId); the area loads the title bar's model and lists that model's sets. resolveAssetSet(set, { start }) returns the ids plus the steps that narrowed them, which the editor's preview shows. Nothing uses a set yet: the planned repeater widget will take one and draw a screen per asset.

Queries run in queryExecution.js (REST calls resolved by restResolver.js, OpHub flows discovered by ophubFlowDiscovery.js); expressions in expressionEval.js.

Patterns to know

The recurring ideas that aren't obvious from any single component. Most exist to let far-apart parts of the screen talk, or to keep DevExtreme and React Flow from redrawing at the wrong moment.

Model data in module globals

23 let variables (asset hierarchy, telemetry, labels, ranges…) in modelData.js, written only there and read everywhere else as live imports. Nothing passes model data as props. Every model is a generic pack keyed by real asset id, so assetQueries.js has one lookup path (getAssetProperties, getAssetPropertySeries, assetTypeIdOf) and no id conversions.

model/modelData.js · model/assetQueries.js

Three shared stores

assetCustomizationStore (who differs from their type, plus the Match/Update actions), displayOrderStore (orders plus setter), and unsavedChangesStore (the Save dot and prompt). Writers publish, any component reads with a hook, including DevExtreme templates that can't take fresh props. Every area with something to save publishes to unsavedChangesStore while it's open: the Configurator's editors, the data areas and Screens.

useAssetCustomizations · useDisplayOrders · useHasUnsavedChanges

One Save button, many editors

Whichever editor is mounted writes its save function into activeSaveHandlerRef. The title-bar Save calls through the ref. Each editor also runs useUnsavedTracker to compare its draft against what it loaded.

PropertyTilesView · RelatedAssetsEditor · AllAssetsEditor

Remount on purpose

Editors read their saved template once, on mount. Selecting a different type or asset, or reverting the open one, changes a React key so they start fresh (nowPreviewRevision). That's also why "act after unsaved changes are resolved" runs on the next render (pendingApplyAssetId).

NowAssetDetail · applyAssetToType

Stable identities for DevExtreme

A DataGrid repaints every row when its columns, data source or drag handler changes identity, which closes any open dropdown in a cell. The Details grids keep rows, columns and callbacks stable across renders on purpose. Canvas position callbacks are stable for the same reason (otherwise they loop).

NowTypeDetailsList · DataListGrid · useCallback handlers

One canvas, four manual modes

Property tiles, related-asset cards and both diagrams all place things by hand through the same ManualLayoutCanvas: it owns node syncing, drag with grid snap, position reporting and align / distribute / arrange. A caller supplies its node component, its grid spacing and the noun for the warnings. The toolbar buttons come from CanvasAlignControls.

canvas/ManualLayoutCanvas.jsx · canvas/CanvasAlignControls.jsx

One class, one stylesheet

The stylesheets are split by area, and every rule mentioning a given class lives in exactly one of them — so the cascade between rules for the same class can't depend on which file loads first. App.js loads them in a fixed order, base first.

operator/styles/*.css

Shared answers, not copied ones

Where two surfaces have to agree, the answer has one definition: relatedAssetRows.js decides which related assets show and in what order (the Details grid and the preview beside it read the same list), and useDiagramSettings owns a diagram's settings, so a control added to one diagram editor appears in the other.

relatedAssets/relatedAssetRows.js · configurator/diagramSettings.jsx

Controlled tab panels

An uncontrolled DevExtreme TabPanel jumps back to its first tab whenever anything nearby re-renders, so every TabPanel here gets its index from lifted state. Any new one should too.

NowAssetTreePanel · NowTypeDetailsList

One handle per area

Every area gives App save() and confirmLeave(), and shell/appAreas.js says what Save is called there. App never needs to know which area is which: the Save button and the leave check call the open area's handle.

shell/appAreas.js · App.js areaHandles

State that outlives its area

The Screens editor's state is a hook App calls (useScreenEditor), not state inside ScreensWorkspace, so the open page and its unsaved edits survive visiting another area. The data definitions live in App for the same reason: Screens reads the queries.

designer/screens/useScreenEditor.js

Edits as plain functions

Every change to a page's container tree is a (tree, …) => tree function in screenEdits.js; the hook wraps it in setContainers and the lock rules. That's what makes the edits testable without a browser.

designer/screens/screenEdits.js · screenEdits.test.js

One resolver per binding type

widgetBindings.js turns a widget's static props plus its bindings into what it renders, with one entry per binding type in BINDING_RESOLVERS. The canvas and the runtime both go through it, so they can't disagree.

designer/screens/widgetBindings.js · ContainerCard

Shortcuts belong to their area

The canvas's Ctrl/Cmd+C and V listen only while Screens is open, and never while you're typing in a field. A document-wide listener with preventDefault once broke paste in every text field in the app.

ScreensWorkspace · useCanvasShortcuts
