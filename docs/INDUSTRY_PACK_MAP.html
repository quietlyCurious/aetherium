Industry Pack Map

How a simulated industry gets from a research brief to the Operator's screen: the Python that writes a pack, the nine JSON files it produces, the registry that lists it, and the four runtime modules that load it and answer questions about it.

Status: one format every model is a generic pack (INDUSTRY_PACK_SPEC.md §6), keyed by real asset id. Refinery, water and wastewater were converted from the older layouts; nothing in src/operator/ knows any model by name. Companion to docs/CODE_MAP.html, which covers the interface itself.

At a glance

The area has three layers that only meet at files on disk: an authoring layer in Python under ModelAndData/, a data layer of JSON under public/data/, and a runtime layer of four JavaScript modules in src/. Python never imports app code and the app never runs Python.

A pack is built left to right, once, by hand-run scripts. The app reads the result at runtime. The dashed arrows are the optional detector path; packs without detectors skip it and the AI tab falls back to plain text.

The pack's files

Each file has a role. The role is what models.json and the loader talk about; the file name is just the default for that role. Every file is keyed by real asset id, so there are no id conversions anywhere between disk and screen.

One invariant ties two of these together: an asset's value in asset-values.json is always the last point of the same key's series in asset-telemetry.json. The time scrubber depends on it, and the validator enforces it.

The registry

public/data/models.json is the one list of models. Both the title-bar model switcher (App.js) and the loader (model/useLoadedModel.js) read it through model/modelRegistry.js, which fetches it once per page load and shares the promise.

Loading a model

Switching models is a full reload of the workspace, never an in-place update. That keeps the whole area simple: nothing has to subscribe to model changes.

  1. Pick. The switcher sets selectedModel; useLoadedModel runs in whichever area is open (OperatorWorkspace or ScreensWorkspace). A model that's already active isn't fetched again.
  2. Fetch. It looks the model up in the registry and fetches every file in parallel. Required files fail the load with a visible message; optional ones become null (a dev server's HTML fallback counts as missing too).
  3. Activate. activateLoadedModel(model, files, results) resets every model variable, then maps each role to its variable (ROLE_TO_VARIABLE), splits properties.json into its lookups, builds the Now-strip tiles from the unit-level assets, parses work-item dates, and applies the pack's own timeline.
  4. Remount. OperatorWorkspaceInner remounts keyed by model, so every view starts fresh against the new data; in Screens, the Data tab's tree and the Create wizard are keyed by model the same way.

One writer, many readers

The model lives in 23 export let variables in modelData.js. ES modules make those live, read-only bindings everywhere else, so only modelData.js can assign them and no view passes model data around as props.

Detectors & explanations

The detector path is what turns an attention item from "the AI says so" into something an operator can check: which signals were compared, against what, what else was ruled out, and how sure the system is. It's optional per pack and entirely offline; the app only ever reads the JSON it produces.

The shared toolkit

FileLinesOwns
detectors/pack.py168Pack.load(repo, model): read-only access to the 8 files (series, children by type, units). The only way a detector sees data.
detectors/blocks.py223Small explainable signal steps: running masks, smoothing, expected-vs-actual residuals, runs above a limit. Each one fits in one operator sentence.
detectors/build.py307The Detector base class (thresholds live in its definition, so the engineer view and the code can't drift), explanation builders, and run_pack().
detectors/preview.py42Renders a pack's explanations.json into one standalone HTML page for content review.

Per pack

  • explain.py defines one Detector subclass per failure mode (wind: HsBearingDamage, FeederTrip, BladeIcing…), runs them all through run_pack() on every asset they apply to, and writes explanations.json. It reports detections with no attention item, and exits 1 if an item goes unexplained.
  • robustness.py reruns generate.py with 10 other seeds into a temp folder and checks every scenario is still found, and nothing extra fires. A detector that only works on the committed data has learned the noise, not the failure.

In the app

InvestigatePanel asks getAttentionItemExplanation(item). With an explanation, the AI tab is ExplanationView (what we see → why we think so → reference examples → ruled out → confidence → what to do), drawn by ExplanationChart. Without one, it's AiInterpretationView. Both share InvestigateStatCards.

The honesty rule

Detectors never read generate.py's scenario constants. If a detector fires, it found the problem in the same data the operator sees, not because it was told where to look.

Rules the area leans on

Ids are forever

Saved Configurator settings are keyed by asset id or type id (TYPE_<level>_<assetType>). Regenerating or converting a pack must keep ids, types and levels stable, or customizations silently stop applying.

assetTypeIdOf · src/*Storage.js

Reset before every load

activateLoadedModel clears all 23 variables first, so a role the new model doesn't fill (say, explanations) can't keep the previous model's data.

resetModelData()

Data only, no code

Adding a model is a folder plus one models.json entry. If a new pack seems to need a code change, that's a sign the spec or the query layer is missing something general.

INDUSTRY_PACK_SPEC.md §9

Deterministic, standard library

Every script uses a fixed seed and only the Python standard library, so anyone can rerun it and get byte-identical files.

generate.py · explain.py · tools/

Evidence sits on the series

An attention item's evidence points fall on the pack's sample grid, and its primary series passes through their values, so the Trend chart and the evidence table always agree.

spec §4 · validator

Budgets are soft limits with reasons

≤ 400 assets (diagram layout time), ≤ 24 units (Now strip width), 2–8 properties per type, ≤ 5 MB per pack. The validator warns; SCENARIOS.md explains any it keeps.

Adding a pack

The full checklist is spec §1 and §13. In short:

# 1  research and scenarios
ModelAndData/industries/<model>/RESEARCH.md, SCENARIOS.md
# 2  generate the 8 files, register, validate
python3 ModelAndData/industries/<model>/generate.py
#    add the entry to public/data/models.json
python3 ModelAndData/tools/validate_industry_pack.py <model>
# 3  detectors (optional, recommended)
python3 ModelAndData/industries/<model>/explain.py
python3 ModelAndData/industries/<model>/robustness.py
python3 ModelAndData/tools/detectors/preview.py <model>
#    add "files": { "explanations": "explanations.json" } to the entry
# 4  check every pack still passes, then click through in the browser
python3 ModelAndData/tools/validate_industry_pack.py --all
